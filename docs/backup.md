# Бэкапы и восстановление

В базе — адреса детей, время, когда их забирают, телефоны родителей и
книга операций с деньгами семей. Потеря этой базы означает конец
сервиса; утечка означает кое-что похуже.

Поэтому правил всего три, и они простые.

## 1. Бэкап шифруется до того, как куда-то уедет

```bash
BACKUP_PASSWORD_FILE=/etc/child/backup.pass tools/backup_db.sh
```

Дамп сжимается и шифруется **потоком**: открытый файл с данными детей не
появляется на диске даже на секунду. Без пароля скрипт откажется
работать — незашифрованный дамп делать нельзя.

По расписанию на сервере:

```bash
0 3 * * * BACKUP_PASSWORD_FILE=/etc/child/backup.pass /path/tools/backup_db.sh
```

Хранится 30 дней (`BACKUP_KEEP_DAYS`), старые удаляются только после
того, как новый получился и оказался не подозрительно мал.

## 2. Пароль от бэкапа хранится отдельно от бэкапа

Три копии, как у ключа подписи (`keystore-backup.md`):

1. менеджер паролей;
2. запечатанный конверт у доверенного человека;
3. **не** на том же сервере и **не** в том же облаке, где лежат дампы.

Пароль потерян = бэкапов нет. Это ровно та же потеря, что и удалённая
база, только обнаруживается она в худший момент.

## 3. Бэкап, который не восстанавливали, — это просто файл

```bash
BACKUP_PASSWORD_FILE=/etc/child/backup.pass \
  tools/restore_check.sh ~/child-backups/child-20260923-030000.sql.gz.enc
```

Скрипт разворачивает дамп во временную базу, считает строки в ключевых
таблицах (семьи, дети, водители, поездки, места, книга операций) и
удаляет базу за собой. Пустая таблица или отсутствующая — провал.

**Когда запускать:**

- после каждой миграции схемы;
- раз в месяц по расписанию;
- обязательно — перед пилотом.

## Восстановление на боевом сервере

```bash
# 1. Остановить сервер, чтобы он не писал в базу во время восстановления.
systemctl stop child

# 2. Развернуть дамп в новую базу (не поверх старой: старая — улика).
createdb child_restored
openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 -pass file:/etc/child/backup.pass \
  -in child-YYYYMMDD-HHMMSS.sql.gz.enc | gunzip | psql -d child_restored

# 3. Проверить глазами: последние поездки, последние записи книги.
psql -d child_restored -c 'select max("createdAt") from ledger_entry;'

# 4. Переключить сервер на восстановленную базу и поднять.
```

**Старую базу не удалять** как минимум неделю: если данные потерялись
из-за ошибки в коде, а не из-за диска, разбираться придётся по ней.

## Что теряется при восстановлении

Между ночным бэкапом и аварией проходит до суток. Потеряются:

- поездки, созданные генератором за это время — **восстанавливаются
  сами**: генератор создаст их заново из шаблонов маршрутов;
- события поездок и подтверждения — частично **придут повторно** из
  офлайн-очередей водительских приложений, они хранят неотправленное;
- записи книги операций за день — **восстанавливаются вручную** по
  подтверждённым наличным, поэтому диспетчеру стоит держать бумажный
  или табличный след дневных пополнений до конца пилота.
