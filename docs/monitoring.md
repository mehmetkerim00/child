# Мониторинг и тревоги

Сервис возит детей. Самое опасное здесь — не ошибка, а тишина: если
уведомления перестали уходить, никто не пожалуется — родители просто
перестанут доверять сервису, и узнаем мы об этом последними.

Поэтому наблюдений три уровня, и каждый отвечает за то, чего не видят
остальные.

## 1. Сервер следит за собой

Каждые пять минут внутренний сторож (`MonitorFutureCall`) проверяет:

| Что смотрим | Когда это проблема |
|---|---|
| Очередь уведомлений | самое старое ждёт 5 минут и больше |
| Недоставленные | 5 и больше за час |
| Задержка SMS | в среднем 120 секунд и больше |
| Поездки без водителя | есть хоть одна на сегодня |
| База | не отвечает |

Найденное превращается в задачу диспетчеру (`systemDegraded`). Одна и та
же беда за час даёт одну задачу, а не двенадцать: список задач должен
оставаться читаемым.

Если бед сразу несколько или отвалилась база, **владелец получает SMS** —
он узнаёт о сбое раньше, чем родители.

Те же цифры владелец видит в приложении: «Отчёты» → состояние сервиса.

## 2. Внешний сторож — о падении сервера

Упавший сервер не может позвать на помощь. Это делает
`tools/watchdog.sh`, и ставить его нужно **не на сервер**: домашний
компьютер, дешёвый VPS, телефон с Termux — что угодно, что не умрёт
вместе с ним.

```bash
# в crontab на другой машине
*/5 * * * * WATCHDOG_ALERT='curl -s -X POST https://sms/send -d msg=' \
  /path/to/watchdog.sh https://api.example.tm
```

Три неудачные проверки подряд — тревога. Одна не считается: связь в
Ашхабаде рвётся сама по себе, а человек, которого будят по каждому
обрыву, быстро научится не реагировать.

Скрипт проверяет `/health` — он живёт на веб-порту (в разработке
`http://localhost:8182/health`) и отдаёт только статус, версию и время.
Длина очереди и расход SMS наружу не отдаются: по открытым счётчикам
видно, сколько у сервиса поездок.

Пока SMS-провайдер не выбран (MVP_PLAN §9), `WATCHDOG_ALERT` можно не
задавать — тревога уйдёт в лог и на экран.

## 3. Ошибки — в Sentry

Реализация подменяемая, как SMS и push. Без переменной `SENTRY_DSN`
ошибки печатаются в консоль сервера, и разработка этим не блокируется.

```bash
SENTRY_DSN='https://ключ@sentry.example.tm/1' dart bin/main.dart
```

Наружу уходит тип ошибки, место и стек — **без персональных данных**:
телефоны из текста вырезаются (`<номер>`). Это проверяется тестом, а не
обещанием: в сообщениях наших исключений бывают имена детей.

Фоновые задачи оборачиваются в `reportingErrors`: упавший ночной
генератор поездок иначе исчезнет молча, а утром дети останутся без
машин.

## Нагрузка

```bash
dart tools/load_test.dart --rides 200 --events 1000
```

Цель из V1_ROADMAP.md — 200 одновременных поездок и 1000 событий в
минуту: это утро города, а не одной школы.

Замер на машине разработки (2026-09-23): 1000 запросов при 200
одновременных — 0 ошибок, медиана 304 мс, p95 675 мс, ~33 800 запросов
в минуту. Запас к цели — тридцатикратный.

Тест проверяет то, что ломается первым: способность сервера и пула
соединений принять всплеск. Он ничего не пишет в базу, поэтому его можно
гонять и по боевому серверу — но лучше ночью.

## Что делать по тревоге

1. **Сервер не отвечает** — поднять; после старта очередь разберётся
   сама, накопленные уведомления уйдут.
2. **Очередь встала, сервер жив** — смотреть логи воркера
   (`ProcessOutboxFutureCall`), проверить SMS-шлюз.
3. **SMS идут долго** — предупредить диспетчера: на уведомления
   полагаться нельзя, важное подтверждать звонком.
4. **Поездки без водителя** — обычная диспетчерская работа, задача уже
   создана.
